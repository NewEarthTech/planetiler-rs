planetiler-rs · the four planet worst cases, and what fixing them taught

First full planet run, 2026-07-22 · planet-260713 (93.9 GB) · r7gd.8xlarge, 32 vCPU, us-west-2 · rs wall 2 h 55 m vs Java v0.10.2 stock 38 m 37 s, same box, same input, both z12 · rs peak VmRSS 117 GB (anon 24 GB) · 13.30 M tiles / 77.9 GB out.
Expanded 2026-07-23 with the campaign that followed: six experiments against worst cases ① and ②, three parked and three shipped, and the pattern that separates them.

What the campaign found: the pipeline was never short of cores

Worst cases ① and ② both look like parallelism problems. One thread governs, the rest of the box idles — the obvious fix is more threads. That fix was built three separate times, against three different stages, and lost every time. Meanwhile three changes that added no parallelism at all — that only made the existing single thread do less work per feature — won every time.

The reason is the same in all six cases: these stages are bound by memory traffic and allocator throughput, not by available cores. Spreading an allocation-bound loop across a pool makes threads contend for the allocator instead of waiting on it. Overlapping two phases that already compete for the same cores just relabels where the time is spent. Neither removes work, and work was the constraint.

Everything below is byte-identical to main at every step — the four-config ladder (monaco, rhode-island default + spill, great-britain z12 sparse) passed on all six experiments, winners and losers alike. None of these results are about correctness; all of them are about where the time goes.

Where the 2 h 55 m went, and where each worst case lives

One bar, one time scale. The numbered dots are the four scenarios below. Java's entire run is drawn underneath at the same scale: it finishes before rs finishes pass 2.

1Pass 2 ways: everything funnels through one allocator-bound thread

Decode scales across the box and keeps up. The single consume thread is 87% of pass-2 wall, so 28+ cores sit idle for 74 minutes — the biggest single lever in the run.

Fixture play: verify GB reproduces this signature (87% consume share) — if it does, GB is the fast proxy and the campaign iterates on flamegraphs there; the planet run demotes to re-baseline.

That play ran. great-britain reproduced the signature exactly — pass 2 at 86–87% consume — so GB became the proxy and the next six experiments happened there. Results below.

perf/overlap-decode-consume

A producer thread reads and decodes blob windows while the caller consumes the previous one, over a rendezvous channel; window halved 64 → 32 so the extra in-flight window costs no memory.

Why it lost: the decode did not find idle silicon — it took cores from the consume's own parallel render. Pass-2 consume_s rose 17.4% while the total moved −0.2%. Total CPU work is conserved; overlapping two phases already competing for 12 cores only relabels the time.

// before: bulk-synchronous — decode stalls, then consume stalls
loop { read(w); decode_par(w); for o in w { consume(o) } }

// parked: producer decodes window N+1 while we consume window N
let (tx, rx) = mpsc::sync_channel::<Vec<T>>(0);  // rendezvous → 1 in flight
scope.spawn(move || tx.send(decode_par(read()))); // …but the pool is already busy

parked  stream 80.25 → 80.08 s

#40 · mimalloc

One line: #[global_allocator]. No structural change at all.

Why it won: it is the direct read of the falsification above. If parallelising an allocation-bound loop makes it slower, the allocator is the constraint — so make every allocation cheaper. Every phase improved at once, which is the signature of an allocator-bound pipeline lifting together.

// src/main.rs — this is the entire change, verbatim
#[global_allocator]
static GLOBAL: mimalloc::MiMalloc = mimalloc::MiMalloc;
// profile −17.5%, render −16.5%, write −9.9%: every phase at once

shipped  wall −12% · peak RSS −17%

#41 · borrow, don't clone

RenderedFeature now borrows its layer name and attributes from the source feature instead of owning them.

Why it won: every covering tile of every feature used to pay a String allocation plus a full BTreeMap deep clone — one allocation per key and per string value — and the very next statement serialized them into the blob and dropped them. Cheaper allocation was #40; fewer allocations is this.

// PreparedZoom::piece — runs once per covering tile, per feature
- layer: feature.layer.clone(),   // 1 String alloc
- attrs: feature.attrs.clone(),   // node + 1 String per key AND value
+ layer: &feature.layer,          // the feature outlives every piece
+ attrs: &feature.attrs,          // borrowed, then serialized and dropped

shipped  every consume term ≈ −7%

#42 · share, don't clone

SourceFeature and VectorFeature hold Arc geometry and tags; attr() copies on write via Arc::make_mut.

Why it won, and the surprise: most of the gain was outside the instrumented consume entirely. SourceFeature shrank 112 → 48 bytes, and pass 2 materializes 43.3 M of them into per-block Vecs on the decode workers before the serial consume drains them.

// SourceFeature / VectorFeature — 112 bytes → 48 bytes
- geometry: Geometry<f64>,          // 56 B inline, deep-cloned per feature
- attrs:    BTreeMap<String, Value>, // 24 B inline, deep-cloned per feature
+ geometry: Arc<Geometry<f64>>,     // 8 B; add() is Arc::clone — a refcount
+ attrs:    Arc<BTreeMap<..>>,      // attr() → Arc::make_mut: copy-on-write

shipped  pass-2 consume −13.6% · RSS flat

#41 · the entry(key.clone()) trap

Shipped alongside the borrow change, and the most portable idea here: BTreeMap::entry takes its key by value, so the idiomatic one-liner allocates a String for every attribute key of every feature.

Why it won: past the first handful of features those keys are always already present, so the allocation was pure waste — 43.3 M features × every tag key, to look up something that was already there.

// record_layer_stats — runs once per attribute per feature
- fields.entry(key.clone()).and_modify(widen).or_insert(ty);
+ match fields.get(key).copied() {              // look up first
+     Some(t) => if t != ty { widen() },        // hot path: zero allocs
+     None    => fields.insert(key.clone(), ty), // clone only if new

shipped  part of #41's −7%

the measurement trap

#42's profile_s fell 32.8% while render_s rose 14.9%. That is re-attribution, not regression: the deep clone had been acting as an accidental prefetch, pulling coordinates into cache right before the render walked them.

Rule: a profile_s/render_s delta is not a verdict on its own. Only the stage total is.

2Merge: one k-way cursor governs, everything downstream starves

369 sorted runs converge on a single min-heap cursor doing 0.64 M entries/s. The run-log deltas prove the encoders and writer never wait on anything but the cursor.

Fixture play: next planet run ships the spill chunks home (or to S3) → replay the merge phase standalone on real planet data; criterion-bench the cursor on the 1 M-entry tile plus a representative stream, so the fix moves the phase and not just the tail. Fresh campaign — the falsified europe-scale parallel-merge branch stays parked as history.

✕Worst case ②'s obvious fix, and the arithmetic that sold it

The partitioned merge is the most expensive negative result in the repo: 1,065 lines, two cloud boxes, byte-identical, memory-neutral after a second revision — and slower on both datasets. It is worth reading precisely because the idea is correct in the abstract.

What it built: into_sorted_partitions splits the sorted stream at tile-floor boundaries so a tile's entries can never straddle two partitions, locating each boundary from sparse (key, byte offset) samples written every 1,024 entries at spill time. Workers then merge partitions independently via positioned reads on a shared handle, behind a claiming window that stops partition i starting until the encoder has drained i−workers.

// parked: one cursor becomes N, split where a tile can never straddle
- for entry in sort.into_sorted()? { .. }           // 1 thread, 0.64 M/s
+ let parts = sort.into_sorted_partitions(target)?;  // N tile-floor slices
+ let merge_workers = parts.len().min(threads / 2);
// boundaries found from (key, offset) samples written every 1,024 entries

The stage it set out to speed up got slower on both boxes. That is the whole finding — the change is byte-identical (GB tile-content hash 800f96337a281878 matched exactly) and memory-neutral, and still loses.

The memory story is its own lesson. The first revision had no claiming window, so workers whose partitions fit inside the channel buffer raced ahead and pre-buffered future ones: great-britain measured 5.74 GB against main's 4.00 GB, +43%. Adding the window put RSS back to 4.24 GB — the fix worked exactly as designed — and the time regression widened from +2.1% to +3.5%. Bounding the memory cost more coordination.

Why the hypothesis was wrong

The figure that motivated it — "~9.5 of the 13 write-minutes are the merge thread" — was arithmetic, not a measurement: 0.9 µs/entry × 625 M entries. Per-entry cost times entry count tells you what a stage would take if nothing overlapped it. The write pipeline already overlaps merge, encode and write across bounded channels.

The rule this bought: no parallelism work starts without a cheap instrumented run proving the target is on the critical path, on the hardware that matters. Probe first, build second. This experiment cost two cloud boxes and a branch to learn something a few minutes of stage-level instrumentation would have shown.

But ② is not closed. The falsification is at extract and continent scale. The planet run's own receipts point the other way — batches_sent − batches_done ≈ 0 for the entire 40 minutes means the encoders really were starved behind the cursor there. Extract-scale evidence does not settle the planet regime, and the parked branch is byte-identical and ready to re-measure against a standalone planet merge replay. That is exactly the fixture play above.

3Monster features: the bbox bound pays ~4.7× memory headroom

The flush predictor counts every tile in a feature's bounding box. A sparse coastline-class geometry crosses the box diagonally and touches a fraction of it. Drawn to ratio: 38 touched of 180 predicted = 4.7×, the number from the planet log.

Fixture play: this is a pure function — harvest the named monster geometries from the checked-in stderr into property fixtures and tighten the bound (e.g. coarse rasterized coverage instead of bbox). No pipeline run needed until the re-baseline.

4Render flush: the predictor held a 39× smaller high-water line

Features buffer in render workers until predicted pieces would cross the bound, then flush in chunks. The 7/20 planet attempt had no bound and died buffering 1.1 M pieces; on 7/22 the largest flush of the whole run was 28,116.

Fixture play: correlate the flush events in stderr with the 1,011 mem samples to find the moment that set the 24 GB anon peak, then bank that window as a replayable flush-storm scenario — the memory-side regression gate for every future lever.

The pattern, and the two rules it cost to learn

Three experiments added concurrency to a stage that looked starved. Three removed work from a stage that looked busy. The scoreboard is unanimous, across three different stages and two different machines.

Rule 1 — probe first, build second. No parallelism work starts without a cheap instrumented run proving the target is on the critical path, on the hardware that matters. Bought with two cloud boxes and 1,065 lines.

Rule 2 — evidence has a shelf life. The overlap experiment obeyed rule 1: it was justified by the #38 probe and by the planet's 12%-CPU shape. It still landed on a stale premise, because #41 and #42 had removed the very idleness it needed — profile_s, the single-threaded stretch decode could have hidden under, had just been cut by a third. Re-probe after the pipeline changes underneath you.

A third habit, cheaper to learn: interleave A/B pairs in both orders. Running the branch second in every pair put it into a box still hot from main's run and understated #42's win; and a two-pair reading that showed "peak RSS consistently −4.7%" was falsified outright by pairs three and four. Four pairs, both orders, before any memory claim.
